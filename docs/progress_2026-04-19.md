#### 失败根因四层分析

**Layer 1: Summary 压缩导致召回力不足**
- LLM 生成的 60-word summary 损失细节（原始 section 平均 300+ words）
- Gold evidence 往往依赖微观 claim（如具体数值、特定术语），而 summary 只保留宏观要点
- 实验验证：所有 summary 配置的 R@1 均 ≤ baseline，证明 summary 文本召回力弱于原始证据

**Layer 2: 语义空间错位**
- Query 目标：检索特定 element（figure/table/formula）的微观 evidence
- Summary 内容：section-level 或 chunk-level 的宏观概括
- 错位：summary 讲"这个章节做了什么实验"，query 问"Figure 3 中 X 轴代表什么"
- 结果：summary 相似度高但 evidence 定位不准（覆盖率提升但精度下降）

**Layer 3: Child normalization 失效**
- 预期：child_alpha=1.0 通过 `boost / sqrt(num_children)` 惩罚大 section（反同质化）
- 实际：topN truncation 已经过滤掉大部分候选，剩余的 group size 差异不大
- 验证：alpha=0.5 vs 1.0 的 MRR 差异 <0.005，说明 normalization 机制无效

**Layer 4: R@1 策略冲突（核心矛盾）**
- 项目目标：优化 R@1 和 MRR（top-1 precision）
- Summary 效果：增加候选覆盖（96.4% queries 有 summary signal）但稀释 top-1 排序
- 数据支持：
  ```
  summary_shadow only:  R@1=0.2008 (-15.8%), queries_with_signal=96.4%
  summary_plus_static:  R@1=0.2400 (-0.9%),  MRR=0.6352 (-0.7%)
  ```
- 结论：summary 是**召回增强工具**（适合 R@100 优化），与 R@1 目标天然冲突

#### Summary 15+ 配置全失败证据链

1. **Scope 维度**：section-level vs chunk-level
   - Section-based best: MRR 0.5937 (baseline 0.6399, **-7.2%**)
   - Chunk-based best: MRR 0.6352 (baseline 0.6399, **-0.7%**)
   - 结论：chunk 粒度更细但仍无法超越

2. **Weight 维度**：0.10 → 0.20
   - w=0.10: MRR 0.6352
   - w=0.15: MRR 0.6325
   - w=0.20: MRR 0.6278
   - 结论：权重越高性能越差（summary 信号越强损伤越大）

3. **TopN 维度**：10 → 20
   - topN=10: MRR 0.6352
   - topN=15: MRR 0.6325
   - topN=20: MRR 0.6276
   - 结论：召回更多 summary 反而稀释精度

4. **Child_alpha 维度**：0.5 → 1.0
   - alpha=0.5: MRR 0.6278
   - alpha=1.0: MRR 0.6305
   - 结论：normalization 效果微弱（<0.3% 提升）

5. **Max_children 维度**：0 (unlimited) vs 5
   - max_children=0: MRR 0.6352
   - max_children=5: MRR 0.6203 (**-2.3%**)
   - 结论：限制 group size 反而有害（截断了有效 summary）

#### 最终决策

**正式关闭 summary 线**，理由：
1. ✅ LLM summary 已充分实现（非启发式）
2. ✅ 实验覆盖 15+ 配置（scope × weight × topN × alpha × max_children）
3. ✅ 最优配置仍低于 baseline 0.7%
4. ✅ 根因明确（压缩损失 + 语义错位 + R@1 冲突）
5. ⚠️ Summary 适合 R@100 召回任务，**不适合本项目的 R@1 优化目标**

后续资源投入 typed_crossdoc（已验证 R@10=0.6406 新高）和 chunk v2 graph rerank（R@1=0.2505）。

## 七、Qrels 构建问题根因分析 — 三层叠加

本周实验中通过 v1_enriched vs v3_n400 对比发现 qrels 构建存在系统性缺陷，导致之前所有 dense retrieval baseline 指标虚高。

### 7.1 问题发现

| Corpus | R@1 | R@5 | R@10 | MRR | Qrels 覆盖 |
|--------|-----|-----|------|-----|-----------|
| v1_enriched (1798 passages) | 0.2389 | 0.5127 | 0.5994 | 0.6081 | **1.00 avg/query** |
| v3_n400 (4772 passages) | 0.1670 | 0.3858 | 0.4968 | 0.4773 | **2.00 avg/query** |

v3 的 R@1 下降 **-7.2pp** 不是 corpus dilution，而是 **qrels 修正后的诚实评估**。

### 7.2 三层缺陷

#### Layer 1: Bridge 段落完全缺失
- **Query 路径包含桥接节点**：`element_ids: ['1709.02012_figure_4', '1703.09207_table_2']`，完整路径 `['1709.02012_figure_4', '1709.02012::p::00010', '1703.09207_table_2']`
- **Qrels 只记录端点**：v1 qrels 仅含 1 个 element_id（更糟），v2 qrels 含 2 个端点但缺 bridge paragraph
- **定量验证**：0 条 qrels 含 `::p::` 格式的桥接段落 ID

#### Layer 2: ID 格式命名空间不匹配
- **LaTeX ref graph 格式**：`{doc_id}::p::{N}` (paragraph nodes)
- **Corpus 格式**：`{doc_id}_{type}_{N}` (elements) 或 `{doc_id}_chunk_{i}` (chunks)
- **结果**：即使 bridge paragraphs 被加入 qrels，也无法匹配任何 corpus passage
- **修复后 section crossdoc**：5135 pid pairs（从 0 增长）证明 ID mapping 可修复

#### Layer 3: Soft Positive 扩展失效
- **预期**：`extend_qrels()` 应将 element 所在 chunk 标为 soft positive
- **实际**：仅 80/1963 chunks 被标记（4.1%）
- **根因**：`sections_overlap(element.section, chunk.section_title)` 依赖 element.section 字段，但多数为空字符串

### 7.3 对历史指标的影响

- **v1_enriched R@1=0.2389 虚高**：只需找到 1/2 个 required elements 即可计入 hit，真实双证据难度被低估
- **v3_n400 R@1=0.1670 是诚实值**：需同时召回 2/2 elements，且无 bridge/chunk 支持
- **Chunk 价值被掩盖**：Chunk 语义上包含 bridge content，但因 soft positive 失效无法获得 credit

### 7.4 修正方向

1. **重建 qrels**：
   - 将 query reasoning path 中所有节点加入 gold standard（含 bridge paragraphs）
   - 建立 `::p::` → chunk_id 映射表（基于 position_idx 或 LaTeX label 匹配）
   - 用 `parent_chunk_id` 字段替代 section_title 做 soft positive 扩展

2. **分离评估粒度**：
   - Element-level retrieval：仅评估 element_ids endpoints（当前 v2 做法）
   - Path-level retrieval：评估完整 reasoning path 召回（含 bridge）
   - Chunk-level retrieval：chunk 作为 primary corpus，element 作为 hard negatives

3. **短期方案**：
   - 用 v3_n400 的 qrels_v2（2.00 avg/query）作为新 baseline
   - 保留 v1 qrels 仅作为 element-only retrieval 对照组

## 八、Chunk Virtual Nodes 构建回顾

### 8.1 生成方法（`scripts/build_chunk_virtual_nodes_v2.py`）

- **输入**：`multimodal_elements_v2.json` (30642 elements, 1145 docs)
- **算法**：按文档遍历 paragraph elements，合并相邻段落直到 token 数 ≈ 400-500（target_length=400, max_length=500）
- **输出**：`data/01_graphs/chunk_virtual_nodes_v2.json` — **1963 chunk nodes**，覆盖 1040/1145 docs (90.8%)
- **字段**：
  - `chunk_id`: `{doc_id}_chunk_{i}`（0-indexed）
  - `doc_id`, `section_title`, `content`, `child_paragraphs`, `token_count`
  - `position_idx`: chunk 在文档中的起始段落位置

### 8.2 实验结果

| Config | R@1 | R@5 | R@10 | MRR | 备注 |
|--------|-----|-----|------|-----|------|
| v1_enriched (1798 elem) | 0.2389 | 0.5127 | 0.5994 | 0.6081 | Element-only baseline |
| v2_chunks (4772 = 1798 elem + 1963 chunk + 1011 dup) | 0.1670 | 0.3858 | 0.4968 | 0.4773 | Direct candidate pool |
| **v2_chunks as rerank context** (0.6B) | **0.2505** | 0.4852 | 0.5391 | 0.6162 | **历史最高 R@1** |

### 8.3 核心结论

1. ✅ **Chunk 作为 rerank 上下文有效**：0.6B 模型 R@1=0.2505 超过 4B baseline (0.2421)
2. ❌ **Chunk 直接进 candidate pool 有害**：R@1 -7.2pp（现确认是 qrels 问题，非 chunk 本身）
3. ⚠️ **Chunk edges 未在 graph rerank 中启用**：`chunk_seq`/`same_chunk` 等 virtual edges 存在但未参与最优配置
4. ⏳ **Chunk + typed_crossdoc 合并未测试**：两条独立路径分别达 R@1=0.2505 / R@10=0.6406，联合潜力未知
