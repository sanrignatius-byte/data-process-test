## 一、按 to-do 详述

### To-do #3 — chunk 平均含几个 element / R@10 低的根因（完成）

在 57 篇 gold 论文上算了一遍：

| 指标 | 数值 |
|---|---|
| 总 chunk 数 | 964 |
| 平均每个 chunk 含几个 element | 1.94（中位 2） |
| 只有 1 个 element 的 chunk | 52% |
| 两个证据落在**同一**个 chunk 的双证据问题 | 2.1% |
| 两个证据落在**不同** chunk 的双证据问题 | 75.5% |

接着做了一层 per-query 的覆盖分析：**R@1 的时候 71% 的问题一个证据都召不到。**

**结论**：用 chunk 当检索单元天然吃亏——检索目标从 1798 个 element 缩到了 964 个 chunk，但 75% 的问题又需要命中两个不同 chunk 才完整。
**落点**：element 当检索单元，chunk 留给下游问答消费。后面不再回头硬推"chunk 做检索"。

### To-do #2 — VL embedding 让图片参与 dense retrieval（跑两轮全负 + bug 已定位）

这条线跑了三轮，每轮死法不一样：

**第一轮（5/2）**
- 上传到 HuggingFace 的那个多模态 embedding 模型的权重**只发了视觉部分，语言部分是随机初始化的**（启动 warning 一堆但当时没注意）
- 整个 query 和 passage 编出来是噪声，R@10 = 0.0021，基本是随机

**第二轮（5/3）**
- 修好环境，权重干净加载，没有 newly initialized 警告
- 但跑出来仍然全面输给纯文本路线：
  - figure：VL 0.54 vs 纯文本 0.71
  - table：VL 0.02 vs 纯文本 0.50
  - formula：VL 0.34 vs 纯文本 0.30（只有这里 VL 略胜）
- 当时归因到"模型本身在 text→multimodal 检索上能力弱"

**5/10 复盘挖到真正的 bug**

| 数据流到哪一步 | figure 带图比例 | table 带图比例 |
|---|---:|---:|
| mineru 原始输出 | 100% | **100%** |
| 中间的多模态元素文件 | 100% | 71% |
| **最终用来检索的语料文件** | 100% | **0%**（只剩 2 条 table，都不带图） |

也就是说：**mineru 给的 table 图片在做检索语料的那一步几乎全丢了。**VL 脚本拿 table 找图片找不到，回退到走文本编码，table 那一路必然归零。

5/3 那次把锅扣在"模型不行"上是**错的**。真正的修法不是改 VL 脚本，而是改语料构建：把 237 个带图的 table 显式作为独立 passage 注入语料 + 带上图片路径。修完再给 VL 一次机会，table 这一路才有公平评测的可能。

**下周排进去**：语料修复 + VL 重跑，大约 1 天 + 半小时 GPU。

### To-do #1 — 摘要+细节式 enrich 参与召回（路线证伪 + 加强方案卡 API）

**5/3 跑了一版**：把已有的视觉描述当"摘要"注入检索语料。两个变体：

| 指标 | 原始 | 替换式 | 叠加式 |
|---|---|---|---|
| dense R@10 | 0.6195 | 0.5106（**−10.9pp**） | 0.5888（−3.1pp） |
| dense R@100 | 0.8636 | 0.7569 | 0.8436 |
| graph rerank R@10 | 0.6913 | 0.5888 | 0.6860（−0.5pp） |

**全线负向，不 promote**。
机制：手上这版视觉描述是脱离具体论文的（典型例子："Histogram of small-valued metric"），而问题用的是论文领域语言。把这种描述塞进 passage，反而冲淡了原本能匹上的领域词。

**加强方案的状态**：mentor 提的多粒度 enrich（一个 element 同时生成"概要句 + 细节句"两段分别参与召回）是另一条路，但**前提是 LLM 能调通**。
公司 API 从 4/21 起返回 401，至今 19 天没恢复，全量 enrich 卡在 40% 没动。
OpenAI 直连可以 fallback，但成本是公司 API 的约 **10 倍**，**等你拍板**。

另外要注意：就算 API 通了，这条加强方案也不能直接 plug-and-play——必须先在 prompt 设计上避开上面那个"视觉描述脱离论文领域"的坑，否则会重蹈本周的覆辙。

### To-do #4 — 文档建图.md 更新（完成）

## 二、这周顺便做掉的事

### 1. 公式检索的瓶颈被推开了一道口子（本周最大的技术信号）

之前公式题的 R@10 在 10 个配置里都卡在 0.56（改图拓扑、改切片、把段落上下文注入公式、把 LaTeX 表面归一化……全都没动）。这周连开三发：

**第一发：caption 注入** — 把公式段落前面拼一段自然语言上下文。结果 R@10 = 0.5600（一动没动）。
**第二发：LaTeX 表面归一化** — `\operatorname` 改写、`\leq` 改写、分数改成 `(a)/(b)` 之类。结果 R@10 = 0.5600（仍然一动没动）。
这两发的含义：之前默认的 embedding 模型对 LaTeX **不是看着别扭，是真编不了**。

**第三发：换一个数学专精的 embedding 模型来编码公式段落，再跟原模型的检索排名做倒数排名融合（reciprocal rank fusion）**

| 指标 | 之前 | 这次 | Δ |
|---|---|---|---|
| 公式题 R@10（全集 179 道） | 0.5600 | **0.6313** | **+7.3pp** |
| 公式题 R@10（平衡冒烟集 25 道） | 0.5600 | 0.6000 | +4.0pp |
| 公式题 R@100（全集） | 0.8636 | 0.9441 | +8.0pp |

**4/17 之后第一个真正推动公式天花板的信号**。原来"模型本身就编码不了 LaTeX"这个结论被部分推翻——只是默认模型那一类编不了。

**有代价**：整体 R@10 跌了 9.7pp（公式段落同时拿到两票，图/表只有一票，所以图/表的相对位置被压下来了）。
**下周怎么修**：只在 query 看起来是公式题时才走融合路径（query 里有数学符号 / 公式关键词），图/表 query 走原来的路径不动。

### 2. 50 道平衡冒烟测试集（mentor 5/2 提的）

按"10 文本 / 10 图 / 10 表 / 10 公式"做。当前问题集合里没有纯文本题，实际比例 17 图 / 17 表 / 16 公式。

**结论**：之前 0.6913 那个上限不是"figure 占评测 56%"造成的偏置——冒烟集上图增益 +1.87pp 在误差范围内，上限是真的。

**但**：图增益**不均匀**——figure +10.3pp / table +8.3pp / **formula 0pp**。
论文里"图增益"的几个 claim 都要明确写"对图、表有效；对公式无效"，不能笼统说。

### 3. mineru → LaTeX 元素级匹配率审计

之前一直只有"大概 50%"和"92%"两种说法，没具体数字。手动核完：

- figure：49.7%
- table：67.3%
- formula：**0%**

92% 是文档级覆盖率（57 篇里 56 篇有数据），跟元素级是两回事。

**这件事解释了第 2 节里 formula 为什么没图增益**：mineru 给的 formula 编号跟 LaTeX 源里的编号完全没打通，图上根本没有边连到 formula 节点，图信号传不进去。

### 4. 用 LaTeX 行号重建 chunk-element 边

按 mentor 要求把字符串模糊匹配换成 LaTeX 行号。把 formula 的元素匹配从 0% 救到 41.2%，重建了 1130 条边、删了 529 条边。

**实测**：拓扑虽然改了，但当前用的图配置走的是桥接节点那条路，不经过 chunk-element 这条边，所以 R@10 完全不动。

**结论**：这件事的工程价值在下游问答 / 训练数据合成那边（对齐准了，证据定位不容易出错），不在检索天花板。检索天花板卡在公式编码上（已被第 1 节推开一道口子）。
